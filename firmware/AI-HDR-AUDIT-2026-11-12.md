# Аудит ускорения AI HDR

Дата: 2026-11-12. Репозиторий: xreal-one-pro-russian.

Аудит без изменения исходников, настроек или прошивки. Расчёты выполнены отдельно в памяти. Новые ядра не реализованы и на очках не измерены.

## Вывод

Первоочередные кандидаты:

1. Представить трилинейную LUT коэффициентами цветовых ячеек: 96 КиБ вместо текущих 291 КиБ.
2. Использовать загруженные коэффициенты сразу для соседних пикселей одной ячейки, сохраняя индивидуальный расчёт каждого пикселя.
3. Написать отдельное NEON tetrahedral ядро: существующая реализация скалярная.
4. Как вариант с потерей точности — локальное аффинное преобразование с полным расчётом в сложных ячейках.

Проверенная математика не доказывает ускорение. Стабильные 60 кадров/с пока не подтверждены.

## 1. Точная трилинейная функция через коэффициенты ячеек

Текущий путь: firmware/lut_fast.c, xreal_compact16_rgb_lut.

Размер таблицы: (17 * 17 * 256 + 512) * 4 = 297984 байта = 291 КиБ. Основные данные занимают 289 КиБ, ещё 2 КиБ — карты осей.

Для каждой из 16³ ячеек исходной 17³ LUT можно заранее вычислить коэффициенты:

    F(r,g,b) = A + Br + Cg + Db + Erg + Frb + Ggb + Hrgb

Здесь r, g, b — локальные нормированные координаты внутри ячейки, а каждый коэффициент содержит три выходных канала. Это точное другое представление трилинейной функции, включая межканальные зависимости.

Проверены две таблицы:

- штатная lut_3d_ai_hdr.cube из локального BIN;
- восстановленный через perf_build.soften_cube вариант strength=0.70, tone=0.35 с настройками функции по умолчанию.

| Проверка | Штатная LUT | Вариант 70% / 35% |
|---|---:|---:|
| Диапазон свободного члена | 0…252 | 0…248 |
| Диапазон остальных коэффициентов | −13…32 | −10…26 |
| Максимальное отличие формулы от float trilinear на 100 000 случайных RGB | ~1,42e−13 | ~1,42e−13 |
| Максимальная ошибка целочисленной модели против округлённого float trilinear | 1 RGB8 | 1 RGB8 |
| Полностью совпавшие RGB-пиксели целочисленной модели | 97,382% | 97,367% |

Свободный член помещается в unsigned byte, остальные коэффициенты — в signed byte. Размер: 4096 * 8 * 3 = 98304 байта = 96 КиБ.

Целочисленная модель:

- коэффициенты расширяются с масштабом 64, то есть шестью дробными битами;
- веса рассчитываются как в c16_weight, в формате Q15;
- полином вычисляется вложенно по R, затем G, затем B;
- умножение моделируется как (value * weight + 16384) >> 15;
- итог округляется и ограничивается диапазоном 0…255.

На выборке промежуточные значения укладывались в signed 16-bit. Это не заменяет полного доказательства диапазонов и проверки будущей NEON-реализации.

Почему может ускорить: меньше таблица, коэффициенты одной ячейки можно загружать последовательно. Почему может проиграть: больше арифметики и распаковки, другой способ использования SIMD.

Для произвольной LUT диапазоны коэффициентов нужно проверять при инициализации; байтовый формат подтверждён только для двух исследованных таблиц. Нужен запасной формат либо существующее ядро.

## 2. Совместный расчёт пикселей одной цветовой ячейки

Сейчас быстрый путь повторно использует результат для полностью одинаковых соседних групп из четырёх пикселей.

Предлагаемый путь: если соседние пиксели имеют одинаковые индексы ячейки LUT, загрузить коэффициенты один раз и рассчитать каждый пиксель со своими координатами.

Для данной сетки все 256 значений оси проверены:

    i = v >> 4
    f = 16 * (v & 15) + i
    локальная координата = f / 255

Это совпадает с текущим разбиением, включая v=255 с нижним индексом 15 и дробью 255.

Доля горизонтальных групп одной ячейки на синтетических кадрах из firmware/tests/test_lut_blocks.py, размер 243×61, seed=20261111:

| Содержимое | Группы по 4 пикселя | Группы по 8 пикселей |
|---|---:|---:|
| film-smooth | 68,0% | 49,1% |
| film-edges | 50,4% | 34,4% |
| grain | 13,2% | 4,0% |
| noise | 0,0% | 0,0% |

Это доли групп в синтетике, не ожидаемый прирост FPS и не статистика реального фильма.

Отличие от прежнего blocks: нет усреднения цвета и восстановления через приблизительный сдвиг. Каждый пиксель вычисляется отдельно; повторно используются только коэффициенты. Неподходящие группы требуют обычного пути.

## 3. Полноценное NEON tetrahedral ядро

Существующее xreal_tetra_rgb_lut вызывает scalar tetra_pixel для каждого пикселя. Ранее проигравший tetra не является проверкой всех возможных SIMD-реализаций алгоритма.

Локальная компиляция текущего исходника с -O2, --target=aarch64-linux-gnu, -mcpu=cortex-a53 и -mfix-cortex-a53-835769 в ассемблер на stdout показала:

- xreal_tetra_rgb_lut: нет ссылок на векторные операнды вида vN.*;
- xreal_compact16_rgb_lut: векторные операции присутствуют, включая SQRDMULH.

Это проверка локального компилятора, не дизассемблирование установленного адаптера и не замер A53.

Что переписать:

- расчёт координат и весов;
- сортировку дробных координат через SIMD-сравнения и выбор;
- совместную арифметику нескольких пикселей либо выходных RGB-каналов;
- загрузки узлов и распаковку.

Текущая tetra-таблица: (4913 + 768) * 4 = 22724 байта, около 22,2 КиБ вместе с картами осей.

Ограничения: произвольные загрузки из LUT не становятся бесплатными от NEON; tetrahedral также отличается от исходной трилинейной функции. По существующим проверкам репозитория для штатного AI HDR встречались отличия до 3 уровней RGB8.

Референс: [NEON LUT-преобразование moxcms в исходниках Chromium](https://chromium.googlesource.com/chromium/src/+/20d6ea4738d277f6413983e3b950aa62758f290c/third_party/rust/chromium_crates_io/vendor/moxcms-v0_8/src/conversions/neon/t_lut3_to_3.rs). Содержит выбор TetrahedralNeon и работу с NEON-интерполяторами. Это пример устройства реализации, не доказательство скорости на A53.

## 4. Локальная аффинная аппроксимация

Для каждой ячейки можно использовать только матрицу и смещение, отбросив смешанные члены. Проверено приближение методом наименьших квадратов по восьми углам.

Для восстановленной LUT 70%/35% доля ячеек с максимальным остатком на углах:

| Порог RGB8 до округления | Доля ячеек |
|---|---:|
| ≤0,5 | 45,24% |
| ≤1 | 92,26% |
| ≤1,5 | 98,12% |
| ≤2 | 99,63% |
| ≤3 | 100% |

Для разности трилинейной и аффинной функций максимум абсолютного остатка по каждому каналу внутри ячейки ограничен углами. Приведённые пороги не включают ошибки будущего fixed-point расчёта.

Возможен гибрид с полным расчётом сложных ячеек. Однако независимо подобранные аффинные функции могут расходиться на границах: нужны проверки градиентов, цветовых ступенек и мерцания на дизеринге. Приоритет ниже точного коэффициентного ядра.

## Другие резервы

- **Подготовка весов compact16:** c16_weight выполняется для каждого пикселя; веса всех 256 значений можно подготовить заранее либо вычислять векторно. Формула индекса через полубайты позволяет исследовать отказ от карт осей.
- **Отображение памяти:** cpu_adapter.c на каждом кадре отображает и инвалидирует три плоскости, затем освобождает отображения. Возможен ограниченный кэш отображений при доказанном времени жизни физических буферов. Инвалидацию входных данных нельзя просто убрать.
- **Полный замер RPC:** текущий convert не включает map/invalidate, unmap и запись результата. Нужны отдельные времена этих этапов, ожидания рабочих потоков и всей обработки.
- **Количество исполнителей:** runtime.c использует три рабочих потока плюс вызывающий. Сравнить 2/3/4 исполнителя при конкуренции с Pilot; четыре не обязательно минимизируют общую задержку.
- **Манифест:** perf_build.py всё ещё описывает autotune compact/compact16, хотя текущий адаптер принудительно выбирает compact16. Это мешает интерпретации отчётов.

## Что не стоит повторять без нового основания

По firmware/PERF.md уже проверялись dense LUT, compact2, prefetch, старый scalar tetra, blocks v1/v2, повторные кадры с копированием, pacing и источники 30/60/90 Гц.

- Источник 30 Гц был отвергнут BSP на One Pro.
- Копирование повторных кадров оказалось дорогим.
- Старые blocks и prefetch проигрывали на устройстве.
- Новый NEON tetra отличается от старого скалярного эксперимента.
- Коэффициентный расчёт по одной ячейке отличается от blocks без усреднения пикселей.

Простые разложения цветовой функции тоже проверены:

| Таблица | Сумма одномерных функций: max ошибки на узлах | Проверенное попарное двумерное разложение: max |
|---|---:|---:|
| Штатная AI HDR | 16,589 | 5,513 |
| Прочитанная установленная LUT | 10,790 | 4,533 |

Это результаты конкретных аддитивных разложений, а не доказательство невозможности любой другой аппроксимации.

## Порядок проверки будущей реализации

1. Отдельно измерить perf13 без копирования повторов и pacing на фиксированном видео.
2. Реализовать коэффициентное ядро и сравнить с compact16; затем добавить общий путь для группы одной ячейки.
3. Проверить все 256³ входных RGB для каждой используемой LUT; отдельно проверить границы ячеек и целочисленные диапазоны.
4. Проверить ARM64-реализацию, границы буферов, strides и обработку полос рабочими потоками.
5. Сравнить на очках одинаковые сцены после прогрева: полное время кадра, медиану, p95/p99 и долю пропусков.
6. Независимо проверить NEON tetrahedral.

Сокращение таблицы, число инструкций и результат на компьютере не заменяют замера на Cortex-A53 очков.
